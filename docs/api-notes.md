# UniFi API research notes

Background research for how to pull per-client usage data out of the
"Proton Promotions" UniFi site remotely (no local LAN access, no on-site
device). Kept here so the reasoning survives even if the collector code
changes later.

## The problem

The UniFi Network app UI has no export feature. The data we want (per-client
name, IP/MAC, bytes used, signal, TX retries — the "Top Clients" panel and
the client detail flyout) is only ever generated by the console's **local**
Network application, and:

- The console (UCG Ultra) is only reachable through unifi.ui remote access —
  there's no VPN or device on the same LAN as the gateway.
- UniFi's officially documented cloud API (**Site Manager API**,
  `api.ui.com/v1`) covers hosts/sites/ISP metrics/devices at an aggregate
  level, but does **not** expose per-client data.

## Two API key types — don't mix these up

| | Local Network API key | Site Manager (cloud) API key |
|---|---|---|
| Created at | Console UI → Settings → Integrations → "Create New API Key" | unifi.ui.com → account/profile → API Keys |
| Works from | Same LAN as the console only | Anywhere, via `api.ui.com` |
| Useful for us? | No — we have no LAN access | Yes — this is the one we need |

We initially found the *local* key panel (screenshotted from the console UI)
and confirmed it does exist and is officially supported, but it requires
direct network connectivity to the console, which we don't have. The
*cloud* key is the one that actually solves the access problem.

## The Connector Proxy

Firmware 5.0.3+ on UniFi OS consoles (UDM/UDR/UCG/UX/UDW/UniFi OS Server —
the UCG Ultra qualifies, it's on 5.1.31) added a **Connector Proxy**: a
relay under `api.ui.com` that forwards requests to a console's local Network
Integration API through its existing remote-access connection. No VPN, no
port forwarding, no on-site hardware required.

```
Base URL:
  https://api.ui.com/v1/connector/consoles/{consoleId}/proxy/network/integration/v1

Auth header:
  X-API-KEY: <site manager api key>
```

Flow:
1. `GET /v1/hosts` (plain Site Manager API, not through the proxy) → find
   the `consoleId` for the UCG Ultra / "Proton Promotions."
2. `GET {proxy_base}/sites` → find the `siteId` (usually "default").
3. `GET {proxy_base}/sites/{siteId}/clients` → per-client data: this is the
   endpoint that should replace the "Top Clients" panel.

There's also a `GET {proxy_base}/sites/{siteId}/clients/{clientId}` for a
single client's detail.

**Confirmed 2026-09-03, blocking issue:** the Connector Proxy requires the
calling account to be the **owner** of the host, not merely an admin.
`GET /v1/hosts` returns `"owner": false` for this account against the UCG
Ultra, and the proxy call fails with:

```json
{"code":"forbidden","httpStatusCode":403,"message":"forbidden: access denied: user is not the owner of this host"}
```

This account (taonga.nhambi@openit.co.zw) has full `admin` permissions on
the site (via `userData.permissions`, all `admin`) but was added as an
*invited* admin rather than being the account that originally
registered/adopted the console — ownership is a separate, non-transitive
flag from admin permissions. **Resolution:** the console owner is known and will generate their own
Site Manager API key (unifi.ui.com → API Keys → Create API Key) and share
it, rather than pursuing an ownership-transfer path. The collector will
use whatever key is set in `UNIFI_API_KEY` — it doesn't matter whose
account it belongs to as long as that account owns the host.

**Unconfirmed from public docs — needs live verification:**
- Exact field names for bytes used (candidates: `rxBytes`/`txBytes`,
  `rx_bytes`/`tx_bytes`, or nested under a `stats`/`uplink` object).
- Whether `/clients` returns *current session* counters (reset on
  reconnect) or a rolling counter — determines whether the collector needs
  to poll frequently and diff, or can trust raw values.
- Exact response envelope (bare array vs `{"data": [...], "offset":
  ..., "limit": ...}` pagination).
- Whether the path segment is `integration` (singular, as seen in the
  UniFi API best-practices reference) or `integrations` (plural, as labeled
  in the console UI's settings panel) — these might not be the same thing.

`scripts/discover.py` exists specifically to pin these down against the real
console before the collector is written, rather than guessing and writing
brittle code against an assumed schema.

**Confirmed 2026-09-03, second blocking issue:** verified against the real
console (owner key, UCG Ultra, Network app 10.6.101, Integration API
version 0.1). Both `/clients` and `/clients/{clientId}` return only:
`type, id, name, connectedAt, ipAddress, macAddress, uplinkDeviceId, access`
— no bytes/usage field at all. Confirmed exhaustively by pulling the API's
own OpenAPI spec (`GET .../proxy/network/api-docs/integration.json`, which
enumerates every route this API supports): there is no per-client
statistics endpoint anywhere in it. The only `statistics/latest` route is
for adopted *devices* (APs/switches/gateway), not individual clients.

**This means per-client bandwidth data is not available through the public
Network Integration API at all, locally or remotely, at its current
version.** It only exists in the classic/private controller API (the
undocumented one the UI itself uses internally, e.g.
`/proxy/network/api/s/default/stat/sta`) — the same one tools like
`unifi-poller`, `aiounifi`, and `pyunifi` target using local admin
credentials rather than an API key. That private API has no cloud/Connector
Proxy equivalent, so it requires genuine local network reachability — an
on-site device is back on the table for per-client granularity
specifically, even though the Connector Proxy fully solves remote access
for site/device-level data (WAN stats, adopted device list, per-device
throughput).

## Why not the historical "Top Clients" numbers directly

The classic private controller API (what the UI itself uses internally, via
`/proxy/network/api/s/default/stat/report/...`) has historical rollups —
that's how "Monthly Data Usage: 75.6 GB" and the Top Clients ranking are
computed. That private API isn't part of the public/documented Network
Integration API, and isn't confirmed to be reachable through the Connector
Proxy. Rather than reverse-engineer an undocumented internal API (fragile,
breaks on UI updates), the plan is: poll the *documented* live-client
endpoint on a schedule and build our own historical record going forward.

## Alternatives considered and rejected

- **Reverse-engineering the unifi.ui browser session** (the relay the
  browser itself uses to show live data remotely) — works today but is
  undocumented, unsupported, and would silently break on any UniFi UI
  change. Also means storing full UI.com account credentials rather than a
  scoped API key.
- **Adding an on-site always-on device** (Raspberry Pi etc.) running a
  collector against the local API directly — this would be the more robust
  long-term option and still worth considering if the Connector Proxy turns
  out to have limits (rate limits, missing historical data, deprecation).
  Rejected for now only because no such device is available at the site.
